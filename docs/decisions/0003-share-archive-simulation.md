# ADR 0003 — Share archive simulation (2026-10-16)

The user authorized implementing a simulation of the proposed M: archive flow, without modifying or deleting real reports. This slice adds planning only. It does not enable live moves, ZIP creation, source deletion, import, or a scheduler.

The intended later workflow is commit inventory, verify archived evidence, copy into `archiviati`, verify the copy and only then remove the source. Monthly archives are named `yyyyMM-MTREPORT.zip`. A report belongs to its collection month in Europe/Rome, not the file modification month or the import month. The monthly due instant is the last day at 23:59 Europe/Rome. Closed months remain due after a missed run; late reports retain their original collection month.

Simulation opens an existing SQLite database read-only, validates schema v1 and tenant, and verifies report bytes against the committed snapshot hash and the hash of the database's raw evidence. Maintenance errors do not disqualify an otherwise successfully acquired report. New, changed, malformed, unreadable, or conflicting files remain blocked and are explicitly listed. No report is imported as a side effect.

Only root JSON files and loose JSON files immediately inside `archiviati` are inspected. Temporary files and unrelated subtrees, including recycle bins, are ignored. Same-name destinations are compared byte-for-byte by SHA-256. Matching staged copies allow a proposed verified-source cleanup; conflicting destinations block the transfer. The plan includes already-staged reports in monthly ZIP candidates. Existing monthly ZIPs block compression pending a separately designed verified update/reconciliation flow; they are never overwritten or trusted just by name. An incomplete archive-directory scan blocks all proposed transfers and compression.

The CLI emits a technical JSON plan and real elapsed progress. Detailed plans contain company filenames/identifiers and must stay outside the public repository. No UI strings or product dependencies are introduced. Plan output is a point-in-time observation, not an executable deletion authorization: any future apply implementation must revalidate all inputs/destinations, verify ZIP contents and manifests, support crash recovery and avoid removing the last verified evidence copy. Backup/restore and actual month-end scheduling remain unimplemented.
