# ADR 0005 — Maintenance review and remote-update direction (2026-10-19)

The user requested a clickable maintenance review card, a per-device issue list, and BIOS/GPU update actions. The review slice reads the latest acquired snapshot only, including explicit BIOS/GPU candidates, subtool failures, reported error text, deferred OEM operations and pending-restart states. The card count and list use the same derived findings. BIOS/GPU filters identify reported candidates from which the user can choose a pilot. These are historical observations, not a live vendor availability check or execution eligibility guarantee.

No remote channel or deployed DMT agent exists yet. The UI must not report an update as sent, scheduled or completed. The update control remains disabled with an explicit agent-not-connected explanation. This slice adds read endpoints only; no arbitrary command execution or package download endpoint is introduced.

The user explicitly revised the initial reboot constraint: a technician contacts the user before a BIOS update; DMT must not issue a remote reboot command; a vendor flasher's autonomous reboot is acceptable after that warning. A coordinated manual reboot remains preferred. Previous no-reboot assumptions must not be presented as guarantees about a vendor flasher. A report's `rebootRequired=false` does not establish an execution guarantee.

Direction for the next slice: a separate Windows DMT agent polls an authenticated HTTPS job channel, bound to enrolled hardware identity and least-privilege job types (BIOS/GPU only), independently of MT. Operator authentication, per-device enrollment credentials, authorization/audit, signed manufacturer packages, model/version preflight, user-contact confirmation, package/tool allowlists and replay-safe job transitions must precede live execution. Never execute URLs/arguments copied unvalidated from inventory reports. No deployment or BIOS/driver execution is authorized merely by displaying a candidate list.

Planned states distinguish queued, preflight, downloading/staged, installing, awaiting_manual_restart or vendor_restart_observed, verifying, completed/failed/unknown. Completion requires a fresh measured BIOS/driver version after the operation, and where necessary after reboot; installer exit status alone is insufficient. Loss of contact during a vendor reboot stays unknown until the agent returns. No DMT reboot job type is planned.

The user will choose a pilot from the reported candidates. Pilot device, reachable HTTPS host, enrollment and vendor execution procedures remain to be selected/implemented after that choice. Do not claim the channel or agent is operational in this review slice. The current host remains an unauthenticated loopback development preview, so it cannot expose privileged remote-update APIs.
